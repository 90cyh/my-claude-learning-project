## 1. 产品概述

### 1.1 产品背景

用户（产品唯一核心用户）有每日记录消费的习惯与需求，但目前缺乏一个顺手、清晰的工具来支撑这件事，导致：

- **记不动**：现有记账产品功能繁杂、广告与理财推销干扰多，打开到完成一次记录的路径太长；
- **看不清**：零散记录无法形成月度/分类维度的结构化视图，记完就忘，数据没有产生洞察；
- **管不住**：没有预算机制，超支发生在事后很久才被感知，记录与「改善财务行为」之间缺少闭环。

### 1.2 产品定位

> **一款轻量的个人记账与财务管理工具：3 秒记一笔，一眼看清钱花哪儿了，用预算管住下个月。**

三个关键词：

| 关键词 | 含义 | 产品上的体现 |
| --- | --- | --- |
| 快 | 记账路径极短 | 首页即记账入口，默认值智能预填，无需跳页 |
| 清 | 消费结构可视化 | 月度账单、分类占比、趋势对比一屏呈现 |
| 管 | 预算约束行为 | 月度总预算 + 分类预算，超支即时提醒 |

> 该定位并非凭空得出，其竞品依据与差异化论证详见第 3 章「竞品分析」。

### 1.3 产品目标

**用户目标（首要）**

1. 单笔记账操作 ≤ 3 步、≤ 5 秒完成；
2. 随时能回答「这个月花了多少、花在哪儿了、比上个月多还是少」；
3. 月底能回答「这个月超预算了吗，超在哪个分类」。

**产品目标（衡量指标详见第 10 章）**

1. V1.0 上线后用户（自己）连续 30 天记账不间断；
2. 记账数据 100% 可导出（CSV），数据主权归用户。

**明确不做（Scope 外）**

以下内容在本产品任何版本均不规划，防止范围蔓延：

- ❌ 社交 / 账单分享 / 面向公众的多租户云服务（V1.0.2 起为**自建服务器**的云端账户，仅服务本人，见 5.9；仍不做公开注册的 SaaS 多租户）
- ❌ 理财、投资、基金股票行情
- ❌ 借贷、信用卡还款提醒、负债管理
- ❌ 广告、会员增值、商业化
- ❌ 发票 OCR、自动记账（V2 前不做，理由见 11.2）

### 1.4 设计原则

1. **记账永远是最短路径**：任何页面 ≤ 2 次点击回到记账入口。
2. **自建优先，隐私第一**：后端服务与数据库均部署在用户自己的设备/服务器上（Node.js + MySQL，V1.0.2），不经任何第三方云；账户为云端账户（用户名+密码，服务端 PBKDF2 哈希，永不明文），数据可随时 CSV 完整导出。
3. **默认值 > 用户输入**：能用规则推断的（日期、常用分类、常用金额）不问用户。
4. **宁缺毋滥**：每个功能必须回答「不做会怎样」，答不上来就砍。

### 1.5 名词解释

| 名词 | 解释 |
| --- | --- |
| 流水 / 交易 | 一笔收支记录，是本产品最核心的数据实体 |
| 分类 | 对交易的人为归类，两级结构（如：餐饮-早餐） |
| 账户 | 资金的存放容器（如：微信、支付宝、现金、招行卡）。**注意与「本地账户」（登录身份，见 5.9）区分** |
| 本地账户 | V1.0.1 起的登录身份：用户名+密码，仅存本机，用于数据隔离与隐私门禁 |
| 预算 | 对某时间范围内某分类（或总计）支出金额的上限约束 |
| 月度账单 | 以自然月为单位的收支汇总视图 |

## 2. 用户分析

### 2.1 目标用户画像

本产品 V1.0 为自用产品，核心用户即产品发起人本人；用户模型同时参考「有记账意愿的个人用户」的共性：

| 维度 | 描述 |
| --- | --- |
| 身份 | 上班族 / 独立开发者，有稳定收入与日常消费 |
| 记账动机 | 想搞清楚钱花哪儿了，控制不必要开支 |
| 使用频率 | 每天记 1~10 笔，多为消费发生后即时记录或当晚集中补记 |
| 使用场景 | 移动端随手记（地铁、收银台、睡前）；偶尔在电脑上回顾分析 |
| 技术水平 | 熟悉数字工具，厌恶复杂配置 |
| 核心诉求 | 记得快、看得清、别打扰我 |

### 2.2 用户故事（User Stories）

按优先级排列，P0 为 MVP 必须满足：

| 编号 | 优先级 | 用户故事 | 验收要点 |
| --- | --- | --- | --- |
| US-01 | P0 | 作为用户，我能在 5 秒内记完一笔支出（金额+分类），这样消费发生时我不嫌麻烦 | 首页直达记账，支持小键盘输入 |
| US-02 | P0 | 作为用户，我能给记录补充备注、日期、账户，这样以后能回忆起这笔钱是什么 | 金额与分类为必填，其余可选 |
| US-03 | P0 | 作为用户，我能查看当月支出的分类占比，这样我知道钱主要花在哪儿 | 饼图 + 排序列表 |
| US-04 | P0 | 作为用户，我能按月对比支出趋势，这样我知道自己是否越花越多 | 至少展示近 6 个月柱状对比 |
| US-05 | P0 | 作为用户，我能修改和删除记错的账，这样数据保持准确 | 列表页可编辑/删除，删除需二次确认 |
| US-06 | P0 | 作为用户，我能把数据导出为 CSV，这样数据不锁死在你的产品里 | 全量导出，字段完整 |
| US-07 | P1 | 作为用户，我能设置月度总预算和分类预算，超支时被提醒，这样我管得住自己 | 超支即提醒，进度条可见 |
| US-08 | P1 | 作为用户，我能管理多个账户并看到各账户余额，这样我知道自己还有多少钱 | 账户余额 = 初始值 + 收入 − 支出 |
| US-09 | P1 | 作为用户，我能记录收入，这样月度视图是完整的现金流 | 收入与支出分账本呈现 |
| US-10 | P2 | 作为用户，我能自定义分类，这样分类贴合我自己的生活 | 支持增删改、排序 |
| US-11 | P2 | 作为用户，我能备份与恢复数据，这样换设备数据不丢 | 导出/导入备份文件 |
| US-12 | P0（V1.0.1） | 作为用户，我能用用户名+密码注册并登录，这样同一台设备上的记账数据有隐私门禁，多人共用设备时互不干扰 | 错误密码无法进入；退出登录后数据不可见；凭证仅存本机且哈希存储 |

### 2.3 核心用户旅程（记录 → 回顾 → 约束）

```
消费发生（如：午饭 28 元）
   │
   ▼ ① 记录（3~5 秒）
打开产品 → 点击记账 → 输金额 28 → 点「餐饮」→ 保存
   │
   ▼ ② 回顾（任意时刻）
打开统计页 → 本月支出 ¥3,420 / 餐饮占比 38% / 环比 +12%
   │
   ▼ ③ 约束（预算）
发现餐饮已用预算 85% → 后半月主动减少外卖
   │
   └──────► 下月预算调整，形成正向循环
```

这条「记录 → 回顾 → 约束」的闭环是产品的灵魂，所有功能设计都必须强化而非打断这个循环。

## 3. 竞品分析

> 竞品分析的目的不是罗列对手的功能清单，而是回答三个问题：**现有产品为什么没有解决 1.1 节的三个痛点？我们从竞品借鉴什么？坚决不学什么？** 本章结论直接支撑 1.2 节的产品定位与第 4 章的需求优先级。
>
> 竞品信息基于公开资料与个人使用体验（截至 2026-11），为一般性描述、非逐版本实测；开发期间若竞品有重大变化（商业模式、数据政策等），需复核本章结论。

### 3.1 竞品分层与分析框架

按「用户今天实际在用什么解决问题」划分，而不是按应用商店分类：

| 层级 | 竞品 | 为什么算竞品 |
| --- | --- | --- |
| 直接竞品（专业记账 App） | 随手记、钱迹、挖财记账、鲨鱼记账 | 与我们解决同一问题：主动记账 + 统计分析 |
| 间接竞品（被动记录） | 微信支付 / 支付宝账单、信用卡 App 账单 | 零成本「自动记账」，是用户放弃主动记账的最大分流 |
| 替代品（通用工具） | Excel / WPS 表格、备忘录、Notion | 自由度最高，记录与分析全部可自定义 |

分析维度对应用户三大痛点与产品两条核心立场，共五个维度：**记账效率（记不动）、分析能力（看不清）、行为约束（管不住）、数据主权、商业化干扰**。

### 3.2 直接竞品分析

#### 3.2.1 随手记（全能型标杆）

- **优势**：功能最全——多账本、借贷报销、生意账、自动记账，统计维度丰富，十余年迭代成熟稳定。
- **劣势（对我们的机会）**：功能堆叠导致首屏信息过载，新用户记一笔之前要先理解「这是记日常账还是生意账」；内置理财导流与会员体系，记账路径上存在商业化干扰；重度功能对个人用户是认知负担而非价值。
- **启示**：**功能全 ≠ 好用**。验证了 1.3 节「明确不做」清单的价值——本产品最大的敌人是向全能型竞品看齐的冲动。

#### 3.2.2 钱迹（极简型标杆，最直接的参照系）

- **优势**：长期主打「无广告、无后台、数据本地」的纯工具定位，与本产品理念最接近，口碑好，证明这条路线有真实用户价值。
- **劣势（对我们的机会）**：多端同步需要注册账号数据上云，对数据主权敏感的用户仍是一道门槛；部分高级能力付费解锁；作为上架 App 受应用商店分发与审核约束，更新迭代慢半拍。
- **启示**：「无广告 + 极简」路线被市场验证，方向可行；同时提醒我们——**数据主权不能只做一半**：本地存储、免费导出、数据不出本机，三件事必须同时成立，缺一个就退化成普通竞品。（V1.0.1 注：本地账户与本条不冲突——它不涉及数据上云，详见 5.9 范围边界表。）

#### 3.2.3 挖财记账、鲨鱼记账等（大众轻量型）

- **优势**：上手门槛低，基础记账 + 统计齐全，渠道占有量大，符合大众「先随便记记」的心智。
- **劣势（对我们的机会）**：内置广告与会员解锁，核心体验被商业化切割——典型表现为部分能力（模板、导出等）圈入会员，工具属性让位于变现指标。
- **启示**：商业化干扰是免费工具类产品的慢性病，病根是「免费产品必须找到付费方」。本产品自用属性天然免疫：**没有盈利压力，就不会有体验扭曲**——这是相对所有商业竞品的结构性优势。

#### 3.2.4 网易有钱（停服案例）

「云端记账 + 自动同步」路线的代表产品，2021 年宣布停止服务，用户多年记账数据面临迁移难题。

- **启示（最重要的反面教材）**：记账数据的生命周期以「十年」计，远长于任何一款产品的生命周期。这一案例直接决定了本产品两条 P0 级决策：**数据本地存储、CSV 免费全量导出（US-06）**。数据主权不是情怀，是刚需。

### 3.3 间接竞品与替代品分析

#### 3.3.1 微信 / 支付宝账单（最大的隐性对手）

- **优势**：零成本、全自动、覆盖大部分线上消费——用户「感觉已经被记录了」，这是主动记账意愿流失的根源。
- **劣势**：只覆盖单一平台渠道（现金、转账、其他平台消费互相割裂）；无预算约束；统计维度服务于平台营销而非个人财务视角；**数据属于平台，离开平台即失明**。
- **启示**：我们 V2 前不做自动导入，等于把「自动」让给对手，因此必须把「手动记账的痛苦」压到最低——**3 步 / 3 秒记账（US-01）不是体验优化，是生存底线**。手动记账产品输给自动账单的唯一原因就是慢。

#### 3.3.2 Excel / Notion / 备忘录（自由度对手）

- **优势**：完全可控、无限自定义，数据 100% 属于自己，记账颗粒度想多细有多细。
- **劣势**：每次记录的操作成本高（开表、找行、填列），对「每天 N 笔」的高频场景太重；统计要自建公式和透视表，普通人维护不动，热情撑不过一个月。
- **启示**：验证了「高频轻量 + 预置统计」的价值；同时借鉴其可迁移性——本产品导出的 CSV 必须能被 Excel 直接打开二次加工（见 5.5 节验收标准）。

| 预算与超支提醒 | ✅（V1.1） | ✅ | ✅ | ✅ | ❌ | 需自建 |

### 3.5 差异化定位：本产品的五个「不一样」

竞品分析的最终输出不是表格，是差异化。本产品不追求「比谁功能多」，追求「在用户核心路径上比谁都干净」：

| # | 差异化主张 | 具体体现 | 反面参照 |
| --- | --- | --- | --- |
| 1 | **零商业化的永久承诺** | 自用产品无盈利压力：无广告、无会员、无理财导流——现在没有，以后也不会有 | 随手记的理财超市、鲨鱼记账的会员墙 |
| 2 | **数据主权三件套** | **自建服务器**（数据在自己手里，不依赖任何第三方云）+ 免费无商业化 + CSV/JSON 免费全量导出，数据随时完整带走 | 网易有钱停服、部分竞品的导出限制 |
| 3 | **3 秒记账的生存底线** | 首页直达、智能默认分类、金额四则运算、连续记账不跳页 | 手动记账败给自动账单的唯一原因是慢 |
| 4 | **一屏只回答一个问题** | 首页只放本月支出一个数字；统计页三个视图各答一问（花了多少 / 花在哪 / 越花越多吗） | 全能型竞品的首屏信息过载 |
| 5 | **一套代码全平台** | 响应式 Web + PWA，免商店分发免审核，手机电脑同一份数据，更新即刷新 | 原生 App 双端开发的成本与更新延迟 |

### 3.6 竞品启示 → 产品决策映射

竞品分析若只停留在「了解对手」，就是无效工作。本章每条启示都必须落到具体产品决策上：

| 竞品启示 | 落到的产品决策 | 所在章节 |
| --- | --- | --- |
| 钱迹验证「无广告 + 极简」路线可行 | 产品定位三关键词（快 / 清 / 管） | 1.2 |
| 网易有钱停服、数据迁移难 | CSV 全量导出定为 P0（US-06）；本地存储定为架构原则；**云端账号长期不做（Q5）** | 4.2 / 8 / 11.2 |
| 微信账单的零成本自动化分流 | 3 步记账定为 P0 且写入设计原则第一条 | 1.4 / 5.1 |
| 随手记的功能蔓延教训 | 「明确不做」清单 + 范围蔓延风险应对 | 1.3 / 11.1 |
| 鲨鱼记账等导出付费墙 | 导出永久免费、字段完整可二次加工 | 5.5 |
| Excel 数据完全可控的优点 | CSV 需 Excel 直接打开不乱码（UTF-8 BOM） | 5.5 验收标准 |

> **本章结论**：市场上不缺记账产品，缺的是「十年后数据还属于你、今天记账不嫌麻烦」的记账产品。本产品的全部差异化，都服务于这一句话。

## 5. 功能需求详述

> 约定：每项功能按「功能说明 → 业务规则 → 交互说明 → 验收标准 → 边界与异常」描述。验收标准必须可测试。

### 5.1 【P0】快速记账

**功能说明**

在首页提供常驻记账入口，点击进入记账表单，用户填写金额与分类后保存，生成一条支出流水。

**表单字段**

| 字段 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| 类型 | 单选 | 是 | 支出 | 支出 / 收入（V1.0 仅支出可选，收入 V1.1 开放） |
| 金额 | 数字 | 是 | 空 | 两位小数，上限 99,999,999.99 |
| 一级分类 | 单选 | 是 | 上次使用的分类 | 见 5.2 分类体系 |
| 二级分类 | 单选 | 否 | 无 | 选一级后出现 |
| 日期 | 日期 | 是 | 今天 | 可改，仅允许选择今天及过去 365 天内 |
| 账户 | 单选 | 否（V1.0） | 默认账户 | V1.0 只有「默认账户」，V1.1 开放多账户 |
| 备注 | 文本 | 否 | 空 | ≤ 50 字符 |

**业务规则**

1. 金额仅接受数字与小数点，自动校验：非负、≤ 2 位小数、非 0（0 元不允许保存，提示「金额需大于 0」）。
2. 日期不允许选择未来日期；允许补记过去 365 天内的账。
3. 保存成功后 Toast 提示「已记一笔 ✓」，停留当前页继续记下一笔（支持连续记账）。
4. 默认记忆规则：一级分类默认为「该用户最近 3 次使用频率最高的分类」，降低选择成本。
5. 金额输入支持简易四则运算（如输入 `12+16` 自动计算为 28），降低分摊记账成本。

**交互说明**

- 移动端：记账表单从底部弹出（Bottom Sheet），大号数字键盘优先；
- 桌面端：弹窗（Modal）形式，支持回车快捷保存（Enter = 保存）；
- 分类选择为图标宫格，一屏最多展示 8 个一级分类 + 「更多」。

**验收标准**

1. 从首页到完成一笔只含金额+分类的记账，点击次数 ≤ 3 次，无页面跳转；
2. 输入金额 0 / 负数 / 三位小数 / 非数字字符，均被拦截并给出明确提示；
3. 选择过去 30 天的日期保存成功，流水正确落入所选日期；
4. 保存后列表与统计在 1 秒内刷新；
5. 连续记账场景：保存后表单保留日期与账户，仅清空金额与备注。

**边界与异常**

- 断网：正常保存（本地存储，无网络依赖）；
- 极端高频：同一秒内多次保存，全部入库，不合并不丢失。

### 5.2 【P0】分类体系（内置）

**功能说明**

V1.0 提供内置两级分类，不可自定义（自定义进 V1.2），保证开箱即用。

**支出分类（9 个一级 + 示例二级）**

| 一级分类 | 图标色 | 内置二级分类 |
| --- | --- | --- |
| 餐饮 | 橙 | 早餐 / 午餐 / 晚餐 / 零食饮料 / 外卖 |
| 交通 | 蓝 | 公交地铁 / 打车 / 加油 / 停车 |
| 购物 | 紫 | 日用品 / 服饰 / 数码 / 美妆 |
| 居住 | 绿 | 房租 / 水电燃气 / 物业 / 家居 |
| 娱乐 | 粉 | 电影演出 / 游戏 / 会员订阅 / 旅行 |
| 医疗 | 红 | 门诊 / 药品 / 体检 |
| 教育 | 青 | 书籍 / 课程 / 培训 |
| 人情 | 黄 | 礼物 / 红包 / 请客 |
| 其他 | 灰 | （无二级） |

**收入分类（V1.1 生效，V1.0 预置不露出）**：工资 / 奖金 / 理财收益 / 退款 / 其他

> 上表「图标色」为色相名，具体色值（含明暗两套）见 6.3.5 分类色板。

**业务规则**

1. 每笔交易必须归属且仅归属一个一级分类；二级分类可选；
2. 统计默认按一级分类聚合，点击可下钻到二级；
3. 分类删除（未来版本）时，其下流水自动归入「其他」，不允许物理丢失数据。

### 5.3 【P0】流水列表

**功能说明**

按日期倒序展示所有交易，按日分组，每日头部显示当日支出小计；支持筛选与编辑、删除。

**页面结构**

```
┌─────────────────────────────┐
│ 筛选栏：月份▾  类型▾  分类▾   │
├─────────────────────────────┤
│ 11月5日 今天      支出 ¥86   │
│   🍜 餐饮-午餐    -¥28       │
│   🚕 交通-打车    -¥58  备注 │
├─────────────────────────────┤
│ 11月4日 昨天      支出 ¥152  │
│   🛒 购物-日用品  -¥152      │
├─────────────────────────────┤
│         [ + 记一笔 ]         │  ← 常驻悬浮按钮
└─────────────────────────────┘
```

**业务规则**

1. 排序：同一天内按创建时间倒序；
2. 每日小计 = 当日所有支出之和（V1.1 起区分收入/支出两列）；
3. 筛选条件可组合（如：11 月 + 餐饮）；
4. 点击任意流水进入编辑页，字段与记账表单一致；
5. 删除需二次确认（弹窗：「删除后不可恢复，确定？」）；V1.0 采用物理删除，不做回收站。

**验收标准**

1. 新增一笔后，列表在对应日期组正确插入并更新小计；
2. 筛选「餐饮」后，仅展示分类为餐饮（含所有二级）的流水；
3. 删除流水后，列表、统计、当日小计同步更新，无残留；
4. 空状态展示引导文案「还没有记录，点击下方按钮记第一笔」。

### 5.4 【P0】统计分析

**功能说明**

统计页提供三个核心视图，回答用户三个问题：花了多少（总览）、花在哪（占比）、越花越多吗（趋势）。

**视图 1：月度总览卡片**

| 展示项 | 计算口径 |
| --- | --- |
| 本月支出 | 所选自然月内全部支出流水之和 |
| 本月收入 | V1.1 上线前显示「—」 |
| 日均支出 | 本月支出 ÷ 当月已过天数 |
| 剩余预算 | （V1.1）总预算 − 已支出，未设置则显示「设预算」入口 |

**视图 2：分类占比**

- 饼图展示所选月份各一级分类支出占比；
- 图例按金额降序，展示「分类名 · 金额 · 百分比」；
- 点击某分类，下钻展示该分类下二级分类构成及流水明细；
- 占比 < 2% 或第 6 名之后的分类合并为「其他」展示（限制同屏色数，依据见 6.3.6），但下钻仍可看全量。

**视图 3：月度趋势**

- 近 6 个月支出柱状图（含当月）；单序列统一用品牌粉，不加图例（见 6.3.1 / 6.3.6）；
- 悬停/点击显示该月总额；
- 当月与上月环比百分比，上涨红色↑、下降绿色↓（红涨绿跌，色值与规则见 6.3.4）；
- 支持切换「按月 / 按周」视角（按周：近 12 周折线）。

**业务规则**

1. 统计页顶部月份选择器默认当前月，可切换至任意有数据的月份；
2. 所有金额展示保留 2 位小数，千分位分隔（¥1,234.56）；
3. 无数据月份显示空状态：「这个月没有记录」。

**验收标准**

1. 手工核对：统计页各分类金额之和 = 月度总览的本月支出（误差为 0）；
2. 修改一笔流水的分类后，两个视图同步更新；
3. 每月 1 日 00:00 后进入统计页，自动切换为新月份且旧月数据完整。

### 5.5 【P0】数据导出（CSV）

**功能说明**

支持全量导出所有交易为 CSV 文件（UTF-8 with BOM，保证 Excel 直接打开不乱码）。V1.0.1 起导出范围为**当前登录账户**的流水。

**业务规则**

1. 导出字段与顺序：`交易ID, 类型, 金额, 一级分类, 二级分类, 日期, 账户, 备注, 创建时间`；
2. 导出范围：默认全部数据；V1.0 不支持按时间筛选导出（进 V1.2）；
3. 文件命名：`简记-记账数据-YYYYMMDD-HHmmss.csv`；
4. 金额导出为纯数字（不含货币符号），便于二次计算。

**验收标准**

1. 导出文件用 Excel 与 WPS 打开，中文无乱码；
2. 导出条数 = 当前账户流水总数（不含其他本地账户的数据）；
3. 备注中的逗号、引号、换行符正确转义（CSV 标准转义）。

### 5.6 【P1】预算管理（V1.1）

**功能说明**

支持设置月度总预算与分类预算，实时展示消耗进度，超支时提醒。

**业务规则**

1. 预算以自然月为周期，每月 1 日自动重置（额度沿用上月设置值）；
2. 总预算与分类预算独立设置，互不校验（分类预算之和可以 ≠ 总预算）；
3. 进度展示分四档：
   - ≤ 60%：绿色进度条，无提示；
   - 61%~89%：黄色进度条，无提示；
   - 90%~100%：橙色进度条，记账保存后 Toast「该分类预算即将用完」；
   - > 100%：红色进度条，记账保存后强提醒弹窗「本月餐饮预算已超支 ¥123」；
4. 记账时若所选分类已超支，保存前给出轻提示（不阻断保存，用户拥有最终决定权）；
5. 预算修改即时生效，历史月份不回溯重算。

> 四档状态色值见 6.3.3；进度条颜色不单独表意，90% 以上档位必须伴随本节规则 3/4 的文字提示。

**验收标准**

1. 设置总预算 3000 元，本月支出累计到 2700 元时记账，触发 90% 档提醒；
2. 修改餐饮预算从 800 → 600，当前已花 750，立即显示超支红色态；
3. 跨月后（模拟系统时间到下月 1 日）进度自动清零，预算额度保持 3000。

### 5.7 【P1】账户管理（V1.1）

**业务规则**

1. 账户字段：名称、图标、初始余额、排序；
2. 账户余额 = 初始余额 + 关联收入 − 关联支出，实时计算，不落库冗余值（防不一致）；
3. 未指定账户的流水计入「未分配」，不参与任何账户余额；
4. 账户删除：其下流水自动转为「未分配」，不物理删除流水；
5. 内置预置账户：微信、支付宝、现金、银行卡（可改名可删）。

> 命名澄清：本章「账户」指**资金账户**（钱包/银行卡），与 5.9 的**本地账户**（登录身份）是两个概念，界面文案用「钱包」或保留「账户」但分属不同页面，不产生混淆。

### 5.8 【P1】备份与恢复（V1.1）

**业务规则**

1. 备份产物为单一 JSON 文件（含当前本地账户的全部流水、分类、预算、资金账户），命名 `简记-备份-YYYYMMDD-HHmmss.json`；
2. 恢复采用**全量覆盖**策略，恢复前强制二次确认并提示「当前数据将被替换且不可恢复」；
3. 恢复前自动生成一份「恢复前快照」备份，防误操作；
4. 备份文件包含版本号字段，未来升级可做数据迁移。

### 5.9 【P0】云端账户（V1.0.1 本地账户 → V1.0.2 升级）

**功能说明**

提供基于「用户名 + 密码」的**云端账户**体系：注册、登录、退出登录与数据隔离。V1.0.1 为本机 localStorage 形态；V1.0.2 起由**自建后端服务**（Node.js + Express，代码位于 003/backend）承载，凭证与数据存于自建 MySQL（004 数据库设计：user / session 表）。服务部署在用户自己的设备/服务器上，不经任何第三方云。

**范围边界（与云端账户的区别）**

| 维度 | V1.0.1 本地账户 | **V1.0.2 云端账户（本版本）** |
| --- | --- | --- |
| 凭证存储 | 仅本机（密码哈希 + 盐） | 自建 MySQL（PBKDF2 哈希 + 盐，永不明文） |
| 换设备登录 | ❌（数据经 CSV 导出 / 备份迁移） | ✅ 同一自建服务器可达即可 |
| 多设备同步 | ❌ | ✅（天然支持，同一库） |
| 忘记密码 | ❌ 本地哈希不可逆，仅可重置账户 | 服务端重置（本地部署可直接重建用户行） |
| 需要后端 | ❌ | ✅（Node.js + Express，自建） |

**注册**

| 字段 | 规则 |
| --- | --- |
| 用户名 | 必填；3~20 字符；仅限中文 / 字母 / 数字 / 下划线；本机内唯一 |
| 密码 | 必填；6~64 字符；建议含字母与数字（软提示，不强制复杂度） |
| 确认密码 | 必填；须与密码一致 |

业务规则：

1. 注册成功后**跳转登录页**，使用新账号登录（V1.0.2：注册接口本身不再直接建立会话）；
2. 用户名重复时提示「该用户名已存在」；
3. 密码**永不明文存储**：服务端使用 Node.js crypto PBKDF2-SHA256（每账户独立随机盐、≥ 100,000 次迭代）生成哈希后写入 user 表；
4. 同一浏览器支持注册多个本地账户，各账户的流水数据完全隔离。

**登录**

1. 用户名 + 密码本地校验；失败统一提示「用户名或密码错误」（不区分具体错因，避免被逐字段试探）；
2. 连续失败 5 次后登录按钮禁用 30 秒（轻量防试探，倒计时对用户可见）；
3. 登录成功后服务端生成随机会话令牌写入 session 表，并经 HttpOnly Cookie 下发，**长期保持**（一年有效），直到用户主动退出——日常使用不需重复登录；
4. 打开应用时的路由规则：前端经 GET /api/auth/me 询问服务端会话状态——有效 → 直接进入首页；无效 → 进入登录/注册页（该页为未登录时唯一可见页面）。

**退出登录**

1. 入口：「我的」页底部「退出登录」按钮；
2. 退出后服务端删除 session 表记录、清除 Cookie 并回到登录/注册页，当前账户数据不再可见；
3. 退出不清除任何数据，重新登录后完整恢复。

**忘记密码（诚实设计）**

本地哈希不可逆且无服务器，**密码无法找回**——这一点必须在注册页与登录页明示（「本地密码无法找回，请牢记」）。提供「重置账户」补救路径：

1. 登录页「忘记密码？」→ 输入用户名 → 系统展示强提醒弹窗「重置将删除该用户名下的**全部记账数据**且不可恢复」；
2. 二次确认：勾选「我已知晓数据将被删除且无法找回」后，「确认重置」按钮才可点击；
3. 重置 = 删除该本地账户及其全部数据，随后可用同一用户名重新注册（数据为空的新账户）。

**交互与视觉说明**

- 登录/注册页遵循 6.2 视觉规范：居中浅粉卡片（圆角 16px）、品牌粉主按钮、微文案「欢迎回来 🌸」（登录）/「记下第一笔吧 🌸」（注册）；
- 本机已注册的账户以胶囊形式列在登录卡片内，点选即填充用户名；
- 无验证码、无第三方登录、无邮箱/手机号字段——表单只有用户名与密码，保持极简；
- 「登录 / 注册」两个 Tab 切换，同一张卡片复用。

**验收标准**

1. 注册新账户后自动进入首页，明细与统计为空（数据隔离生效）；
2. 注册同名第二个账户被拦截；账户 A 退出后登录账户 B，看不到 A 的任何流水、统计与导出内容；
3. 错误密码登录提示「用户名或密码错误」；连续 5 次失败后登录按钮禁用并显示 30 秒倒计时；
4. 退出登录 → 刷新页面 → 仍停留在登录/注册页（会话已清除）；
5. 查询 MySQL user 表，password_hash / salt 中找不到明文密码；
6. 重置账户流程完成后，该用户名可重新注册，进入后数据为空；
7. 已登录状态下刷新/关闭再打开应用，无需重新登录（会话保持）。

**边界与异常**

- 浏览器隐私模式：功能可用，但关闭窗口后会话与数据可能不被保留（浏览器特性，登录页脚注提示）；
- 断网：注册、登录、退出全部正常（纯本地校验，无网络依赖）；
- 清除浏览器数据：等同删除全部本地账户与数据（与 V1.0 行为一致，风险应对见 11.1）。

### 6.3 配色方案

> 本章色值全部经配色验证脚本实测（WCAG 对比度与色觉模拟），数据随表格给出；8 个彩色分类在全对模式下的色觉弱对为数学极限，按 6.3.6 的结构性规则兜底。

#### 6.3.1 设计气质与品牌色

气质关键词：**粉嫩、可爱、俏皮**。粉色通过「表面色调 + 品牌色 + 分类淡染」三层进入界面；文字保持高对比深梅色，可爱不以可读性为代价。

| 角色 | 浅色主题 | 深色主题 | 用途与实测对比度 |
| --- | --- | --- | --- |
| 品牌粉（图形主色） | `#ec4f93` | `#f27fb1` | 选中态、开关、单序列图表、图标点缀；浅卡 3.32:1（图形 ≥3:1 达标）/ 深卡 7.06:1 |
| 品牌深梅（文字级粉） | `#b0306b` | `#f47fb4` | 链接、次级操作等小字场景；5.83:1 / 7.06:1（小字 AA 达标） |
| 主按钮 | 底 `#f981b6` + 字 `#4a1029` | 底 `#f27fb1` + 字 `#3d0f24` | 6.33:1 / 6.54:1 |

**禁用组合**：白字配任意粉底（实测最高 4.37:1，不达小字标准）。粉色系底上的文字一律使用深梅 `#4a1029`。

#### 6.3.2 中性色与主题令牌

| 令牌 | 浅色 | 深色 | 实测对比度（对各自卡片面） |
| --- | --- | --- | --- |
| 页面底 plane | `#fbf3f6` | `#170f14` | — |
| 卡片面 surface | `#fefafc` | `#211722` | — |
| 主文字 | `#3d2230` | `#f7ecf2` | 13.81 / 15.07 |
| 次文字 | `#7a5c6b` | `#d3b9c8` | 5.68 / 9.54 |
| 弱化文字（轴标签、时间戳） | `#9d8392` | `#9c7f90` | 3.33 / 4.84 |
| 网格线（1px 实线） | `#f2dfe7` | `#362633` | 装饰性 |
| 描边 hairline | `rgba(61,34,48,.10)` | `rgba(255,255,255,.10)` | 装饰性 |

说明：深色主题**不是浅色的自动反色**，而是独立选定的一套值（梅紫暗调），两套各自验证。开发以 CSS 自定义属性按令牌命名，明暗切换只替换变量值。

#### 6.3.3 状态色（预算四档）

| 档位 | 浅色 | 深色 | 浅底实测 | 触发规则（同 5.6） |
| --- | --- | --- | --- | --- |
| ≤ 60% 安全绿 | `#2fa254` | `#4ec17f` | 3.16 ✅ | 无提示 |
| 61~89% 注意黄 | `#d99e14` | `#d9a52e` | 2.29 ⚠️ | 无提示 |
| 90~100% 预警橙 | `#e06a2a` | `#e8824f` | 3.24 ✅ | 记账后 Toast 提醒 |
| > 100% 超支红 | `#d64560` | `#e87a8c` | 4.16 ✅ | 记账后强提醒弹窗 |

深底实测四色全部 6.2~7.7:1 ✅。黄色对浅底天然不足 3:1（色相明度极限，业界通行处理方式），因此硬性规定：**进度条恒伴随百分比文字与图标，颜色永不单独表意**。未填充轨道用该档位色的浅一阶同族色（或中性 `#f6e7ee` / `#3a2a37`）。状态色为保留色，禁止挪作分类图表用色。

#### 6.3.4 收支与涨跌语义色

| 语义 | 浅色 | 深色 | 实测对比度 |
| --- | --- | --- | --- |
| 支出 / 上涨（坏） | `#c22e4e` | `#f2879e` | 5.35 / 7.22 ✅ |
| 收入 / 下降（好） | `#1a7a42` | `#58c98a` | 5.20 / 8.38 ✅ |

规则：红涨绿跌（本产品语境「支出上涨 = 坏」）；流水列表金额小字用语义色；统计大数字用主文字色（避免满屏红）；涨跌必须带 `▲/▼` 符号及「vs 上月」文字，不得仅靠颜色区分。

#### 6.3.5 分类图表色板（实测验证）

| 分类 | 浅色 | 深色 |
| --- | --- | --- |
| 餐饮 | `#e8752e` | `#cd6229` |
| 交通 | `#4292e8` | `#4789dd` |
| 购物 | `#9a5cd8` | `#9478d8` |
| 居住 | `#2ca257` | `#35a55e` |
| 娱乐 | `#e65697` | `#e35f96` |
| 医疗 | `#d43f56` | `#d14b5c` |
| 教育 | `#17a091` | `#1f9483` |
| 人情 | `#c99510` | `#b58410` |
| 其他 | `#9d8392` | `#9c7f90` |

「其他」取中性灰（即弱化文字色），有意与彩色分类区分。**分类图标**：底 = 该分类色 12% 淡染圆角方块，图形 = 该分类色——粉嫩观感的主要载体放在图标淡染层，图表色块本身保持达标深度，两者两全。

**验证记录**（配色验证脚本，全对模式：饼图中任意两色都可能相邻）：

- 浅色板 @ `#fefafc`：明度带 PASS、彩度 PASS；对比度不足 3:1 仅 2 色（餐饮橙 2.89 / 人情黄 2.61，黄为色相明度极限）→ 由 6.3.6 文字兜底规则覆盖；最弱色觉模拟对：人情黄↔餐饮橙 ΔE 1.6（绿色盲），最弱正常视觉对：教育青↔居住绿 ΔE 8.3；
- 深色板 @ `#211722`：8 色明度带 / 彩度 / 对比度逐项全部 PASS；已知弱对按色相族记录（两主题一致）：粉↔红、蓝↔紫、黄↔橙；
- 8 色在全对模式下无法全部达标是数学极限（非调色问题），因此 6.3.6 的结构化兜底为**必选项**；
- 开发合并前需整板复跑一次：`node validate_palette.js "<8色hex>" --mode light --surface "#fefafc" --pairs all`（深色加 `--mode dark --surface "#211722"`）。

#### 6.3.6 图表配色使用规则

1. **同屏色数上限**：饼图最多 5 个分类 + 「其他」（与 5.4 下钻规则一致）；扇区间 2px 表面色间隔；
2. **文字永不穿数据色**：标签、图例、数值一律用中性色令牌；分类识别靠图标与色点，不靠给文字上色；
3. **单序列图表统一品牌粉**（如月度趋势柱状图），不加图例——标题即说明；
4. **悬停 tooltip 为默认能力**；饼图旁的分类列表（名 · 金额 · 占比）即文字兜底视图，图形与文字两套呈现缺一不可；
5. **分类色跟随分类实体**：排序、筛选导致名次变化时颜色不重排；
6. **无障碍**：所有图表数据在列表/明细存在文字等价；V1.2 预留 45°/135° 纹理填充通道（打印与全色觉障碍场景）。

### 6.4 关键交互决策

1. **记账入口三处常驻**：首页主按钮、明细页悬浮按钮、快捷键 `N`（桌面端）——保证「记账永远是最短路径」原则落地；
2. **首页大数字只放一个**：本月支出。不给用户多个数字要权衡，聚焦「管住花销」（布局见 6.2）；
3. **统计页不做时间自由区间**：V1.0 只支持自然月切换。自定义时间区间是伪需求，用户真实问题都以月为单位（发薪、房租、信用卡账单）；
4. **登录只挡在第一次**（V1.0.1）：会话长期保持，登录页只在无会话时出现——隐私门禁不能变成每次打开的摩擦，否则违背设计原则 1。

| --- | --- | --- |
| id | INTEGER PK | 自增主键 |
| user_id | TEXT FK | 所属本地账户（V1.0.1 起补齐） |
| category_id | INTEGER FK | 为空 = 总预算 |
| amount | REAL | 月度额度 |
| updated_at | TEXT | 修改时间 |

> 预算按「当月生效值」存储，每月 1 日重置进度但沿用额度，因此无需月份维度字段。

### 7.5 本地账户表 user（V1.0.1）

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| id | TEXT PK | 是 | 随机 UUID（避免自增 ID 泄露账户数量与注册顺序） |
| username | TEXT | 是 | 用户名，本机内唯一，3~20 字符 |
| password_hash | TEXT | 是 | PBKDF2-SHA256 哈希（≥ 100,000 次迭代），**永不明文** |
| salt | TEXT | 是 | 每账户独立随机盐 |
| created_at | TEXT | 是 | ISO 8601 时间戳 |

**会话（session）**：`{ user_id, login_at }`，存于本机，退出登录时清除。

**存储实现建议（localStorage 形态）**：

- `jianji.users` —— 本地账户列表（含哈希与盐）；
- `jianji.data.<user_id>` —— 该账户的交易数据（物理隔离，键级隔离优于行级过滤，防实现疏漏导致跨账户泄漏）；
- `jianji.session` —— 当前会话；
- `jianji.settings.<user_id>` —— 该账户的偏好设置（主题等）。

## 8. 非功能需求

| 类别 | 需求 | 验收标准 |
| --- | --- | --- |
| 性能 | 页面首屏加载 | ≤ 1.5 秒（本地数据 10 万条流水内） |
| 性能 | 记账保存响应 | ≤ 300ms |
| 性能 | 统计页渲染 | 1 万条流水内 ≤ 1 秒 |
| 性能 | 登录校验响应（V1.0.1） | PBKDF2 计算完成即可感知反馈，全程 ≤ 1 秒 |
| 兼容 | 浏览器 | Chrome / Edge / Safari 最近两个大版本 |
| 兼容 | 响应式 | 375px 宽度（iPhone SE）至 1920px 全部可用，移动端优先设计 |
| 隐私 | 数据存储 | 全部本地（localStorage / IndexedDB），无任何数据上报；**账户凭证（密码哈希与盐）同样仅存本机** |
| 隐私 | 网络权限 | 断网状态下全部核心功能可用（含注册/登录） |
| **安全** | **密码存储（V1.0.1）** | **仅存 PBKDF2-SHA256 哈希（独立随机盐、≥ 10 万次迭代），任何界面与存储中不出现明文密码；登录失败提示不区分用户名/密码错误；连续失败 5 次锁定 30 秒** |
| 可靠性 | 数据完整性 | 保存失败时明确报错，绝不静默丢数据；写操作采用事务；**数据读写严格按会话 user_id 隔离，杜绝跨账户可见（验收见 5.9）** |
| 可维护 | 技术形态 | Web App（响应式），后续可封装为 PWA / 桌面端 |
| 可访问 | 无障碍 | 颜色对比度 ≥ WCAG AA；图表同时有文字数据兜底（不止靠颜色区分）；完整配色规范与验证记录见 6.3 |

## 10. 成功指标

自用产品不设北极星指标的虚荣版本，只设「自我可感知」的标准：

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| 记账连续性 | V1.0 上线后连续 30 天每天 ≥ 1 笔 | 核心指标：说明「快」做到位了 |

| 数据准确率 | 月末抽查 10 笔，分类正确率 ≥ 90% | 说明默认分类体系合理 |
| 预算留存（V1.1 后） | 连续 3 个月设置并使用预算 | 说明「管」形成习惯闭环 |
| 登录零摩擦（V1.0.1） | 日常打开应用 100% 免登录（会话保持） | 说明隐私门禁没有变成使用摩擦 |
